0. WHAT CHANGED THIS ROUND (CLAUDE)
================================================================================

Two changes, both reasoned from first principles, not from more ST-doc
reading:

1. App/Inc/host/uart4_mode.h
   UART4_MODE: UART4_MODE_DAMIAO_BRIDGE -> UART4_MODE_TELEM

   Context: UART4_MODE_DAMIAO_BRIDGE was added in the very last commit before
   RTOS work started (14eb426, "damiao dmj4310 enable working"). It
   reconfigures UART4 to 921600-8N1 and arms a self-re-arming 1-byte
   interrupt-driven RX (HAL_UART_Receive_IT) from host_uart_bridge_init(),
   called unconditionally from app_init(). This has been active on every
   boot since before RTOS work began, regardless of whether the physical
   Damiao debug UART is actually connected on the bench right now. If it
   isn't, a floating RX line at that baud can pick up noise as spurious
   start bits and fire continuously at NVIC priority 6 -- more urgent than
   SVCall/PendSV (priority 15), which FreeRTOS's one-time first-task handoff
   depends on. Flipped back to TELEM (inert unless HOST_TRANSPORT_UART is
   also set) to remove this variable while debugging the scheduler.

2. Decoupled USB init and the heartbeat/TIM6 start from the scheduler
   entirely, moving both back into main() unconditionally, matching the
   pre-RTOS baseline (14eb426) ordering exactly:

   Core/Src/main.c:
     MX_TIM6_Init();
     control_loop_start();      // moved here, was inside ControlTask
     ...
     app_init();
     MX_USB_Device_Init();      // moved here, was inside StartDefaultTask
     ...
     MX_FREERTOS_Init();
     osKernelStart();

   Core/Src/app_freertos.c:
     ControlTask and StartDefaultTask no longer call control_loop_start()/
     MX_USB_Device_Init() themselves -- those already ran before either task
     exists.

   App/Src/plant/control_loop.c:
     control_loop_tick() (TIM6 ISR) now guards the vTaskNotifyGiveFromISR/
     portYIELD_FROM_ISR call with BOTH g_control_task_handle != NULL AND
     xTaskGetSchedulerState() == taskSCHEDULER_RUNNING -- same pattern
     already used in stm32g4xx_it.c's SysTick_Handler. Necessary because
     TIM6 now starts long before the scheduler exists; without this guard
     there's a narrow window (after MX_FREERTOS_Init() sets the task handle,
     before osKernelStart() actually runs the first task) where a tick
     could call portYIELD_FROM_ISR before the scheduler has bootstrapped.

   Rationale (for whoever picks this up next): nothing about FreeRTOS
   requires USB init or the heartbeat to live inside a task body. That
   coupling was a convention (matching ST's own StartDefaultTask examples),
   not a requirement. The only thing that actually needs scheduler
   preemption is the per-tick actuator/servo work in ControlTask and the
   host-link polling in HostLinkTask (so a blocking diagnostic probe can't
   stall actuator control) -- USB enumeration and the heartbeat blink have
   no inherent dependency on the scheduler ever successfully starting.
   Decoupling them means a scheduler-bootstrap failure no longer takes down
   USB/heartbeat with it, which also makes the next symptom much more
   informative than it would have been otherwise.

2. WHAT THIS DOES AND DOES NOT RULE OUT
================================================================================

RULED OUT (fairly high confidence):
  - "USB coupled to scheduler bootstrap" as the sole/primary explanation.
    MX_USB_Device_Init() now runs in main(), before MX_FREERTOS_Init() or
    osKernelStart() exist at all -- in the exact same execution context as
    the working pre-RTOS baseline. It still doesn't enumerate. Whatever is
    wrong with USB is not simply "it's stuck inside a task that never
    runs" anymore, because it isn't in a task anymore.

NOT RULED OUT -- genuinely open, listed without ranking to avoid
pigeonholing before there's real evidence:

  (a) A hang or crash still happens somewhere between control_loop_start()
      and MX_USB_Device_Init() -- i.e. inside app_init(). CAN bus start,
      MCP2518 SPI/EXTI init, mutex creation, host_link_init all happen here.
      TIM6 fires via hardware interrupt independent of what main() is doing,
      AS LONG AS interrupts stay globally enabled -- so if app_init() were
      merely slow (blocking on retries), PC3 should still be toggling by
      now. That it's fully solid suggests either interrupts got globally
      masked at some point, or not enough wall-clock time has passed yet.
      UNCONFIRMED: how long was the board powered before this was checked?
      500ms is one heartbeat half-period; if it was checked within under a
      second of power-up this may just be "hasn't ticked yet," not "will
      never tick."

  (b) A hang or crash between app_init() returning and MX_USB_Device_Init()
      actually completing (i.e. inside MX_USB_Device_Init() itself, or the
      HAL/USBD stack it calls into).

  (c) A configASSERT trip somewhere in MX_FREERTOS_Init() / osKernelStart().
      configASSERT is currently: `taskDISABLE_INTERRUPTS(); for(;;);` -- a
      totally silent infinite loop with interrupts masked and NO LED
      activity of any kind (not Error_Handler's blink, not HardFault's
      blink -- literally nothing). This would explain PC3 freezing at
      whatever state it was last in (SET, matching what's observed) and
      TIM6 going silent (interrupts masked), simultaneously. This is
      consistent with the data but NOT confirmed -- there is no direct
      evidence it's an assert specifically versus (a) or (b) above just
      not having had enough time, or some other silent loop.

  (d) Something MCP2518-EXTI-related (priority 6, enabled during
      app_init(), same general shape of concern as the UART4 issue but not
      yet checked with the same scrutiny -- edge-triggered so a genuine
      storm is less likely than UART4's case was, but not ruled out).

  (e) Plain hardware/wiring explanation for USB specifically (cable, port,
      connector) -- included only for completeness. Given the user's
      correct pushback that nothing else in the environment changed except
      firmware, this should be treated as low-probability and not
      investigated before (a)-(d), but it costs nothing to swap the cable
      once while debugging something else.
