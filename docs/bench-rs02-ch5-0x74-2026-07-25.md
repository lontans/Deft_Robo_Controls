## Step 2 — dual CH5 (`0x70` slot 22 + `0x74` slot 23) validate

Date: 2026-07-25T200447Z. User confirmed `0x70` reattached and raised a hypothesis: the earlier `found=0`/`raw_frames=0` silence on `0x74` might trace to a mechanical/connector issue, since disconnecting `0x74` earlier "was easy — maybe too easy."

Ran a scoped scratch script (`~/dual_ch5_validate.py` on the Jetson, not committed — bus5/slots 22–23 only, no CH6/Damiao touched) implementing the sibling-safe reset order from [base-robstride-mcp.md](peripherals/base-robstride-mcp.md): reset **all** RS IDs on the bus first (`0x70` then `0x74`, no probe interleaved), *then* enable-only probe (`reset=False`) each.

### Sibling-safe reset + probe

```
reset 0x70 ok=True  reset 0x74 ok=True
0x70: found=1 pos=+0.0186..+0.0313 (run-to-run)
0x74: found=1 pos=-0.2104
```

Both IDs `found=1` immediately after the bus-wide reset sweep — no interleaving fault.

### Connector-flake check (targeted at the user's hypothesis)

20x back-to-back enable-only probes of `0x74` alone, then repeated again on a second full run (40 probes total across two runs): **40/40 found=1, 0 misses**, position stable to within CAN quantization (`-0.2100`/`-0.2104` alternating, sub-mrad noise). **No evidence of an intermittent/mechanical connection fault at rest** — the connector reads as solidly seated under static probing.

### CFG + dual hold

CFG enabled slot 22 (`0x70`) + slot 23 (`0x74`) only (all other slots quieted), then a short 10 s dual hold at kp=20/kd=1, 200 Hz apply loop.

**Run 1 (no soft-gain ramp, straight to kp=20/kd=1): FAIL.** `0x70` held fine (peak err 0.031 rad), but `0x74` showed a peak error of **6.49 rad** somewhere in the 10 s window — this was a large *transient*, not sustained: final fb (`-0.2108`) matched the target (`-0.2104`) closely, so it settled correctly. Root-caused to my own validate script skipping the soft gain ramp-in (`u = 0.0→1.0` over ~0.6 s) that the production base-rig scripts (`seed_holds()` in `base_bus56_lab.py`) always do before a hard hold — jumping straight to full kp/kd on a freshly-CFG-enabled slot can snap through a large transient on first apply.

**Run 2 (added soft-gain ramp before the hold, plus transient-vs-settled instrumentation): PASS.**

```
slot22(0x70): n=2000 fb=+0.0190 hold_err_peak=0.0038 @t=0.00s  last1s_peak=0.0038
slot23(0x74): n=2000 fb=-0.2104 hold_err_peak=0.0008 @t=2.64s  last1s_peak=0.0004
frames=2000  fb_hz~200.0
OVERALL: PASS
```

Both slots track their hold target to <4 mrad peak error, no faults, no rail-wrap, no reset-sibling perturbation. CDC released cleanly after (`fuser /dev/ttyACM0` empty, no residual process).

### Step 2 PASS / FAIL

**PASS.** Sibling-safe reset: both `found=1`. Flake-check: 40/40, no mechanical/intermittent signal. Dual hold: PASS on the soft-ramped run — both motors settle and hold within gate.

**On the user's connector hypothesis**: the probe-level evidence (40/40 clean reads under repeated at-rest polling) does not support an intermittent mechanical fault. The one large excursion seen was reproduced as a software ramp-in issue in the *validation script itself* (fixed, and the fix is consistent with how the production bring-up scripts already avoid this by ramping gains in). That said, static probing doesn't load the connector under torque/vibration the way sustained motion would — if the "too easy to unplug" concern persists, the next data point would be a load/vibration check during actual motion (e.g. a longer continuous segment) rather than another static probe, since this test can't rule out a marginal connector that only shows up under mechanical stress.
